## 我完成的具体工作

我负责把记账本这个本地 Web 页面的骨架、样式和录入入口做出来，三个文件共 878 行（提交 `a7d0830`）。

**页面结构。** 按 README 3.9 的前端契约，我把页面拆成录入、账单、统计三块，并预留 9 个固定容器：`record-form`、`record-message`、`filter-panel`、`record-list`、`list-message`、`stats-panel`、`stats-message`、`category-chart`、`monthly-chart`。容器 ID 一旦定死，负责列表和看板的同学写脚本时就不用再问我页面长什么样；主页面只引 `entry.js` 和 `list.js` 两个 module，`dashboard.js` 由 `list.js` 自己 import，避免重复加载和重复初始化。

**样式。** 桌面端两列（录入栏 360px + 内容区自适应），900px 以下转单列，560px 以下收紧内边距与字号；支出用红色、收入用绿色；输入框有焦点态和 `aria-invalid` 错误态。另外给列表和看板留了表格、按钮、图表容器的基础样式，图表容器固定 220px（手机 180px）高度，防止 Chart.js 画上去之后父容器高度塌陷成 0。

**录入交互。** 默认日期取浏览器本地年月日拼接；收入/支出用分段控件切换；金额从“元”文本换算成整数“分”；提交前做一遍与后端同口径的校验（真实日期、金额 1—999999999 分、类别 1—20 字符、备注 ≤200 字符）；请求期间禁用提交按钮，成功后派发 `records-changed` 事件，让列表和统计各自去刷新，而不是由我直接调用它们的刷新函数。

**联调后的调整。** 合进主分支后，组长在集成阶段把类别输入从 `datalist` 改成了 `select`，并按收入/支出分别给选项（`09e4ac2`、`b2be29e`），日期占位和账单列表高度也做了调整（`8c73ee5`）。这些改动我复核过，方向是对的：下拉比自由输入更容易保证类别合法，代价是前端要多维护一份类别表，现在的 `entry.js` 里由 `syncCategoryOptions()` 在类型切换时同步选项，并清掉不属于新类型的已选类别。

## 遇到的问题与解决方法

**一、金额换算的浮点误差。** 一开始想用 `parseFloat(text) * 100` 转成分，随手试了几个数就发现 `19.99 * 100` 得到 `1998.9999999999998`，直接取整会变成 1998 分，少一分钱。改成按小数点拆字符串：整数位 ×100 加上补足两位的小数位，全程整数运算，`12.50 → 1250`、`100.5 → 10050` 都对。金额输入框也特意用 `type="text"` 配 `inputmode="decimal"`，而不是 `number`——`number` 会接受 `1e5` 这种科学计数法，格式没法完全由自己控制。

**二、默认日期的时区。** 最初想用 `new Date().toISOString().slice(0, 10)`，但 `toISOString()` 走的是 UTC，北京时间凌晨 0—8 点会算成前一天，记账日期就会错一天。改成用 `getFullYear()`/`getMonth()`/`getDate()` 自己拼 `YYYY-MM-DD`，和用户看到的日期一致。

**三、非法日期其实轮不到我拦。** 测 `2026-02-30` 这种日期时才发现，`<input type="date">` 在赋值阶段就把非法值丢掉了，`value` 直接变空串。也就是说浏览器原生控件已经挡住大部分非法日期，前端这一层真正需要兜的是“空值”，合法性判定还是得靠后端。这让我重新想了一遍“前端校验该做多细”。

**四、网络异常时不能断言“没保存”。** 我最初在 `catch` 里写的是“网络异常，未保存成功”，联调时被指出这个结论不成立：请求可能已经到达服务端，只是响应中断了。后来改成“暂时无法确认保存结果，请先刷新账单核对，再决定是否重试”。这是这次印象最深的一处——技术上没错的代码，语义上可能是错的。

**五、验证工具本身也会踩坑。** 想用无头浏览器做验收，`playwright install` 装不下来、装完路径也是空的，最后改成直接指定本机 Edge 的 `executable_path` 才跑通。写断言之前先确认工具能跑，这一步不能省。

## 团队协作体验

这次最有用的是**先定契约再并行写代码**。README 3.9 把容器 ID、表单字段名、事件名都写死了，我不用等 1 号的 `app.py` 落地，就能用一个临时的桩服务（Flask 假接口）把录入流程跑通。

对接点比较明确：和 1 号对接的是错误响应结构（`error`/`code`/`field`），我直接读 `body.error` 展示、按 `body.field` 标红对应输入框，没有另造一套文案；和 6 号只通过容器和 `records-changed` 事件耦合，我坚持不直接调用他的刷新函数，否则他还没交代码之前我的页面就跑不起来；4 号的统计接口不接受 `limit`，所以前端构造统计请求时必须把列表的 limit 去掉，这一条写在契约里，省了一次返工。

不太顺的地方是公共文件。`templates/index.html` 和 `main.css` 在集成阶段被别人改动时我看不到过程，只能事后看 diff 复核。下次应该在契约里再约定一句“谁的区块谁改”，或者至少改完在群里说一声改了哪几行。

## 收获与改进

1. 契约写得越具体，协作成本越低。容器 ID、字段名、事件名提前定死，六个人并行开发几乎没有互相等。
2. 前端校验和后端校验要分清职责：前端是为了少发无效请求和给即时提示，最终判定必须在后端，所以我没有把校验做重，只做到“能提前拦住明显错误”。
3. 验证要能拿数字说话。我没有停在“页面能打开”，而是用桩服务加自动化脚本跑了 31 条断言：`12.50 → 1250`、`100.5 → 10050`、`12.345`/`0`/`-5`/`abc` 都被拦住且不发请求、后端返回 400 时能显示后端文案且不误报成功、390px 宽无横向溢出。全部模块合并后，我又在真实后端上跑了一遍完整链路：记一笔 12.50 元支出和一笔 100.00 元收入，统计显示总收入 100.00、总支出 12.50、结余 87.50，与 README 验收清单里的数字一致。
4. 下次改进：先写最小桩服务再写页面，把“能跑”提前到写代码的第一分钟；公共文件的改动走 PR 评审，而不是直接推主分支。
